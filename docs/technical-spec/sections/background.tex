\section{Technical Background}
\label{sec:technical-background}

\subsection{Graphs and Graph Representations}
\label{sec:graphs-and-representations}

A graph is a mathematical structure used to represent a collection of entities
and the relationships between them. Formally, a graph is defined as

\begin{equation}
  G = (V, E),
  \label{eq:graph-definition}
\end{equation}

where $V$ is a set of vertices, or nodes, and $E$ is a set of edges connecting
those nodes. The symbols $|V|$ and $|E|$ denote the number of nodes and edges,
respectively. In a directed graph, an edge $(u,v) \in E$ has a source $u$ and a
destination $v$; in an undirected graph, the relationship is symmetric. A node
feature vector $\mathbf{x}_v \in \mathbb{R}^{F}$ is a list of $F$ numerical
values describing node $v$. An edge feature vector
$\mathbf{e}_{u,v} \in \mathbb{R}^{D}$ similarly contains $D$ values describing
an edge. These features contain the data on which a GNN operates, while the
edges determine which nodes can exchange information.

For a directed graph, the incoming neighborhood of a node $v$ is

\begin{equation}
  \mathcal{N}(v) = \{u \in V \mid (u,v) \in E\},
  \label{eq:incoming-neighborhood}
\end{equation}

and its in-degree is $\deg^{-}(v)=|\mathcal{N}(v)|$. For example, if
$\mathcal{N}(v)=\{a,b,c\}$, then $v$ has three incoming neighbors and
$\deg^{-}(v)=3$. The analogous definitions using edges $(v,u)$ give the
outgoing neighborhood and out-degree. For an undirected graph these
distinctions disappear, and the degree is simply
$\deg(v)=|\mathcal{N}(v)|$. The degree distribution describes how node degrees
vary across the graph. A graph in which degrees vary widely is
degree-skewed: many nodes may have only a few neighbors while a small number of
nodes have hundreds or thousands. Degree distribution therefore captures
structural information that is not conveyed by $|V|$ and $|E|$ alone.

Throughout this document, \emph{graph topology} refers to the pattern of
connectivity between nodes. Graph size and topology are related but distinct.
Two graphs $G_1$ and $G_2$ can satisfy

\begin{equation}
  |V_1| = |V_2| \quad\text{and}\quad |E_1| = |E_2|
  \label{eq:same-size-different-topology}
\end{equation}

while having very different neighborhoods, degree distributions, and local
connectivity patterns. Consequently, equal-sized graphs need not induce the
same pattern of computation in a GNN.

For an unweighted graph, the adjacency matrix
$A \in \{0,1\}^{|V|\times|V|}$ records which edges exist. Row $i$
represents the source node, and column $j$ represents the destination node:

\begin{equation}
  A_{ij} =
  \begin{cases}
    1, & \text{if } (i,j) \in E, \\
    0, & \text{otherwise}.
  \end{cases}
  \label{eq:adjacency-matrix}
\end{equation}

Because $A$ has one row and one column for every node, its dimensions are
$|V|\times|V|$ and it contains $|V|^2$ entries. This representation makes graph
operations convenient to express using linear algebra. Explicitly storing every
entry is wasteful, however, when $|E| \ll |V|^2$, meaning that the graph has far
fewer edges than entries in its dense adjacency matrix. Sparse graphs are
therefore commonly stored using only the edges that exist, in a representation
such as coordinate format (COO) or compressed sparse row
(CSR)~\cite{pytorchSparseDocs}.

COO stores one source index and one destination index for every edge. In the
unweighted case, this requires two index arrays of length $|E|$; an additional
array stores values when edges are weighted. PyTorch Geometric commonly stacks
the source and destination arrays into an integer tensor called
$\texttt{edge\_index}$ with shape $2\times|E|$. Its first row contains source
indices and its second row contains destination indices~\cite{pygEdgeIndex}.
COO is easy to construct and makes it straightforward to assign work to individual edges, including in parallel.

CSR instead groups entries by matrix row. It stores a row-pointer array of
length $|V|+1$ and a column-index array of length $|E|$, with optional edge
values. Under the source-row convention used here, the entries from
$\texttt{row\_ptr}[i]$ up to, but not including,
$\texttt{row\_ptr}[i+1]$ identify the out-neighbors of node $i$. This layout
removes the repeated row index and makes traversal of each stored row direct. If
destinations were used as rows instead, each row would list incoming neighbors;
either convention represents the same directed graph when used consistently.
Ignoring optional edge values, the storage requirements are summarized by

\begin{equation}
  \text{dense: }O(|V|^2), \qquad
  \text{COO: }O(|E|), \qquad
  \text{CSR: }O(|V|+|E|).
  \label{eq:graph-storage-complexity}
\end{equation}

Here, Big-O notation describes how storage grows with graph size, not how long
an operation takes. Constant factors, such as COO storing two index arrays, are
omitted.

For example, consider a directed graph with

\[
  V=\{0,1,2,3\}, \qquad
  E=\{(0,1),(0,3),(1,2),(2,0),(2,3)\}.
\]

Topology describes which connections exist; representation describes how
those connections are stored. The same graph can use different storage layouts,
and those layouts can change how a GNN accesses data.


\subsection{Graph Neural Networks}
\label{sec:gnns}

A Graph Neural Network (GNN) learns from a graph whose nodes represent entities and whose edges represent relationships between them. Node features describe the entities, while edge features, when present, describe the relationships. A GNN uses these connections and features to combine information from neighboring nodes and make predictions.

For example, in a citation graph, nodes represent papers and directed edges represent citations. A paper's feature vector might describe its content. To predict the paper's subject, a GNN can use both its own features and information from connected papers. The graph therefore determines which data contributes to each prediction.

A neural network applies learned operations, such as matrix multiplication, to its inputs. During training, it adjusts parameters called \emph{weights} to improve predictions. During inference, it uses those fixed weights to make predictions. This project focuses on inference.

\subsubsection{Node Features and Representations}

For a graph $G=(V,E)$, let each node $v$ have a feature vector $\mathbf{x}_v\in\mathbb{R}^{F}$, where $F$ is the number of features per node. Collecting these vectors as rows gives the feature matrix

\[
  X\in\mathbb{R}^{|V|\times F}.
\]

A GNN transforms input features into intermediate vectors called \emph{node representations}. These vectors support the prediction task and may have a different width from the input features.

Let $\mathbf{h}_v^{(\ell)}$ denote the representation of node $v$ after layer $\ell$. A layer is one stage of the model's computation, and the initial representation is simply the input:

\[
  \mathbf{h}_v^{(0)}=\mathbf{x}_v.
\]

The representations at each layer can likewise be stored as a dense matrix

\[
  H^{(\ell)}\in\mathbb{R}^{|V|\times F_\ell},
\]

where $F_\ell$ is the representation width at that layer. The graph connectivity is generally stored separately in a sparse format.

\subsubsection{Computation Across the Graph}

In a typical neighborhood-based GNN layer, each node collects information from its neighbors, combines that information, and computes an updated representation. Combining neighbor information might involve summing or averaging their vectors. The layer can then apply a learned transformation and an elementwise nonlinear function to produce its output.

An elementwise nonlinear function changes each value independently. For example, the commonly used rectified linear unit, or ReLU, replaces negative values with zero:

\[
  \operatorname{ReLU}(z)=\max(0,z).
\]

These nonlinear functions allow stacked layers to express relationships that a sequence of linear transformations alone could not.

A GNN layer often combines graph-directed data access and reduction with dense numerical computation. The graph determines which rows of the feature matrix are accessed and combined. Learned transformations operate on the resulting vectors, often through matrix multiplication. The exact order and form of these operations depend on the architecture.

Each layer gathers information from immediate neighbors. Stacking layers lets information from more distant nodes influence a prediction.

\subsubsection{Predictions and Static Topology}

The final representations are used to compute predictions. For node classification, the model produces a score for each possible category at each node. In the citation example, these categories could be paper subjects. For graph-level prediction, the model first combines node representations into a single vector describing the graph, then computes an output from that vector.

Node numbers are labels, not features. If nodes are renumbered consistently, node predictions should follow the new numbering, while a prediction for the whole graph should stay the same. Small floating-point differences can occur if renumbering changes the order of aggregation.

For this project, the important distinction is between model parameters, feature values, and graph topology. Parameters specify the learned transformations. Features supply the numerical input. Topology determines which nodes exchange information. A static topology can therefore be reused across inference runs even when feature values change.

\subsection{Message Passing}
\label{sec:message-passing}

Message passing describes how a GNN uses graph connections to update node representations~\cite{gilmerMessagePassing}. For each edge, a message is constructed from its source toward its destination. Each destination combines its incoming messages, then updates its representation. These are conceptual stages; an implementation may combine them into fewer GPU operations.

\subsubsection{Message Construction}

For an edge $(u,v)$, the layer computes a message from source node $u$ to destination node $v$:

\[
  \mathbf{m}_{u\rightarrow v}^{(\ell)}
  = M_\ell\left(\mathbf{h}_u^{(\ell)},\mathbf{h}_v^{(\ell)},\mathbf{e}_{u,v}\right),
\]

where $M_\ell$ is the message function and $\mathbf{e}_{u,v}$ contains any edge features. The superscript $\ell$ identifies the layer. Not every model uses destination features or edge features, and the message function may contain learned parameters.

In a simple case, the message is just the source node's representation:

\[
  \mathbf{m}_{u\rightarrow v}^{(\ell)}=\mathbf{h}_u^{(\ell)}.
\]

Other models transform the source vector, scale it by an edge weight, or compute a contribution that depends on both endpoints. An edge therefore specifies where information flows, while the message function specifies what information is contributed.

\subsubsection{Aggregation}

Each destination node combines the messages from its incoming neighbors:

\[
  \mathbf{a}_v^{(\ell)}
  = \operatorname{AGG}_\ell\left(
    \left\{\mathbf{m}_{u\rightarrow v}^{(\ell)}\mid u\in\mathcal{N}(v)\right\}
    \right).
\]

The aggregation function reduces a variable number of message vectors to a fixed-width vector. Common choices include elementwise sum, mean, and maximum. For sum aggregation,

\[
  \mathbf{a}_v^{(\ell)}
  = \sum_{u\in\mathcal{N}(v)}\mathbf{m}_{u\rightarrow v}^{(\ell)}.
\]

The result should not depend mathematically on the order in which neighbors are processed. Floating-point implementations can nevertheless produce small differences when the reduction order changes.

For a node with no incoming neighbors, sum aggregation produces a zero vector. Mean and maximum need a separately defined result because there are no messages to average or compare.

\subsubsection{Node Update}

The layer uses the aggregate to compute the next node representation:

\[
  \mathbf{h}_v^{(\ell+1)}
  = U_\ell\left(\mathbf{h}_v^{(\ell)},\mathbf{a}_v^{(\ell)}\right),
\]

where $U_\ell$ is the update function. It may combine the node's current representation with the aggregate, apply a learned transformation, and then apply a nonlinear function.

For example, a simple update is

\[
  \mathbf{h}_v^{(\ell+1)}
  = \operatorname{ReLU}\left(
    W_{\mathrm{self}}^{(\ell)}\mathbf{h}_v^{(\ell)}
    + W_{\mathrm{neighbor}}^{(\ell)}\mathbf{a}_v^{(\ell)}
    + \mathbf{b}^{(\ell)}\right).
\]

Here, vectors are treated as column vectors. In this example, each message and its aggregate have width $F_\ell$. Both weight matrices therefore have shape $F_{\ell+1}\times F_\ell$, and the bias vector has length $F_{\ell+1}$. The matrices and bias are learned during training and remain fixed during inference.

This example gives the node's own features a separate contribution. Another common approach adds self-loops to the graph so that each node contributes a message to itself. These choices are part of the model definition and must be preserved during optimization.

\subsubsection{Example on a Small Graph}

Consider the directed graph introduced earlier:

\[
  E=\{(0,1),(0,3),(1,2),(2,0),(2,3)\}.
\]

Suppose the current node representations are

\[
  \mathbf{h}_0=\begin{bmatrix}1\\2\end{bmatrix},
  \qquad
  \mathbf{h}_1=\begin{bmatrix}3\\1\end{bmatrix},
  \qquad
  \mathbf{h}_2=\begin{bmatrix}2\\4\end{bmatrix},
  \qquad
  \mathbf{h}_3=\begin{bmatrix}0\\1\end{bmatrix}.
\]

Using source representations as messages and sum aggregation, node $3$ receives contributions from nodes $0$ and $2$:

\[
  \mathbf{a}_3=\mathbf{h}_0+\mathbf{h}_2
  =\begin{bmatrix}3\\6\end{bmatrix}.
\]

The other aggregates are

\[
  \mathbf{a}_0=\mathbf{h}_2,
  \qquad
  \mathbf{a}_1=\mathbf{h}_0,
  \qquad

\]

Each node then applies its update function. All messages in this layer use the representations available at the beginning of the layer. Updating one node must not cause another node to consume its new representation within the same layer.

\subsubsection{Relationship to Sparse Computation}

For this simple message function, sum aggregation can also be written as a sparse matrix operation. Under the source-row adjacency convention used earlier, $A_{uv}=1$ when an edge goes from $u$ to $v$. If node representations are stored as rows of $H^{(\ell)}$, the matrix of incoming aggregates is

\[
  S^{(\ell)}=A^{\mathsf{T}}H^{(\ell)}.
\]

Because the adjacency matrix uses source nodes as rows, its column for node $3$ marks the edges entering node $3$. After transposing, row $3$ selects the representations of nodes $0$ and $2$, whose sum gives node $3$'s aggregate. Each edge contributes a feature vector, giving work proportional to $|E|F_\ell$ for straightforward sum aggregation.

An implementation can process edges individually and accumulate into destination rows, or group edges by destination and perform a reduction for each node. These approaches express the same computation but distribute work and access memory differently. More complex message functions may require additional edge-level computation and cannot always be expressed as a single sparse matrix multiplication.

Graph topology determines which feature vectors are read and how many messages each destination aggregates.

\subsection{GNN Computation on GPUs}
\label{sec:gnn-computation-on-gpus}

A GPU executes a GNN by mapping its operations onto many parallel threads. The dense transformations within a layer resemble those used in other neural networks, while neighborhood computation follows the sparse connectivity of the graph. These parts of the workload have different execution characteristics and may require different ways of assigning work to threads.

To understand this distinction, consider the simple sum aggregation introduced earlier:

\[
  S=A^{\mathsf{T}}H,
\]

where $A$ uses source nodes as rows and $H$ contains node representations. A subsequent learned transformation might compute

\[
  Y=SW,
\]

where $W$ is a dense weight matrix. The first operation follows graph connectivity to collect feature vectors. The second performs a regular matrix multiplication. Although both belong to the same layer, their memory-access patterns and opportunities for parallelism differ substantially.

\subsubsection{Dense Feature Transformations}

A dense transformation applies the same weight matrix to every node's representation. If there are $N$ nodes, an input feature width $F_{\mathrm{in}}$, and an output feature width $F_{\mathrm{out}}$, the computation has the form

\[
  H\in\mathbb{R}^{N\times F_{\mathrm{in}}},
  \qquad
  W\in\mathbb{R}^{F_{\mathrm{in}}\times F_{\mathrm{out}}},
  \qquad
  Z=HW.
\]

The earlier node-update example treats each node vector as a column. Here, node vectors are stored as rows of $H$, so the weight matrix multiplies on the right.

Its arithmetic work is proportional to

\[
  NF_{\mathrm{in}}F_{\mathrm{out}}.
\]

The matrix dimensions define a regular iteration space. GPU implementations can divide the output matrix into small rectangular blocks, called \emph{tiles}, and reuse input values and weights while computing each block. This reuse increases the amount of arithmetic performed per value fetched from memory. Depending on the data type and matrix dimensions, implementations may also use specialized matrix-multiplication hardware.

Bias addition and activation functions operate on the resulting elements. These operations can sometimes be combined with the matrix multiplication or with each other, avoiding separate kernel launches and intermediate memory traffic. Such combinations are called \emph{kernel fusion}.

\subsubsection{Neighborhood Aggregation}

Neighborhood aggregation has a different structure. For each destination node $v$, sum aggregation computes

\[
  \mathbf{s}_v=\sum_{u\in\mathcal{N}(v)}\mathbf{h}_u.
\]

The graph specifies which source vectors are read, and the number of contributions varies with the destination's in-degree. Unlike dense matrix multiplication, the input accesses follow stored node indices rather than a regular rectangular traversal.

There are several ways to distribute this work. An edge-based implementation assigns work to edges. Each edge reads its source features and contributes to its destination's output. Different edges can target the same destination, so concurrent updates require coordination, often through atomic additions. An atomic addition updates a memory location without losing contributions from other threads, but competing updates can limit throughput.

A destination-based implementation instead assigns a group of threads to a node or a group of nodes. Those threads traverse incoming edges and reduce the corresponding source features. Grouping edges by destination makes this traversal direct and can avoid global atomic updates when one thread group owns the entire output row. However, nodes with substantially different degrees require different amounts of work, which can leave some thread groups running much longer than others.

Feature dimensions provide another axis of parallelism. Threads can cooperate across the elements of a feature vector as well as across neighboring nodes. The appropriate assignment therefore depends on feature width and degree distribution, not only on the total number of edges.

\subsubsection{Memory Access and Intermediate Storage}

When a node's feature values are stored next to one another, threads can often fetch adjacent values together. Accesses to different source rows remain dependent on graph connectivity. Nearby destination nodes may reuse some source vectors, or they may access widely separated regions of the feature matrix.

This makes data reuse less predictable than in dense matrix multiplication. Graph ordering and sparse layout can affect locality even when the underlying mathematical operation remains unchanged.

An implementation may also explicitly construct a message vector for every edge before aggregation. If each message has width $F_m$, this intermediate contains

\[
  |E|F_m
\]

elements. Writing those messages to device memory and reading them again during reduction can introduce substantial traffic. When the message function permits it, computing contributions directly within the aggregation kernel can avoid this intermediate storage.

The benefit of fusion depends on the workload. A fused kernel may reduce memory traffic but require more registers or complicate work distribution. Fusion is therefore an execution choice to evaluate rather than an assumption that it always improves performance.

\subsubsection{Computation Order}

Some GNN operations admit more than one mathematically equivalent evaluation order. For a simple linear neighborhood transformation,

\[
  Y=(A^{\mathsf{T}}H)W=A^{\mathsf{T}}(HW).
\]

The first form aggregates input features before applying the dense transformation. The second transforms each node's features first and then aggregates them. Their aggregation work is proportional to $|E|F_{\mathrm{in}}$ and $|E|F_{\mathrm{out}}$, respectively. Consequently, changing the order can change the width of the data moved through the sparse operation.

This equivalence applies to the stated linear computation. Nonlinear functions between operations, edge-dependent transformations, or changes to normalization can prevent the same rearrangement. Floating-point evaluation can also differ between the two orders even when they are equivalent in exact arithmetic.

\subsubsection{Performance Implications}

The dominant cost of a GNN layer depends on its dimensions and graph structure. Dense transformations can account for much of the arithmetic when feature widths are large. Neighborhood operations can instead be limited by memory traffic, competing updates, or uneven work distribution. A layer may exhibit several of these limits at different stages.

Kernel-level improvements must also be assessed within the complete inference workload. Reducing aggregation time has limited effect if dense transformations dominate total latency. Likewise, converting the graph to a different layout or reordering its nodes introduces preprocessing costs and may require additional storage.

For a static graph, preparation can be reused across repeated executions. Let $T_{\mathrm{setup}}$ be the additional one-time cost of preparing a specialized strategy, including graph analysis, data conversion, or compilation. If each run takes $T_{\mathrm{base}}$ with TorchInductor and $T_{\mathrm{specialized}}$ with the new strategy, specialization pays off after $R$ runs when

\[
  T_{\mathrm{setup}}+R\,T_{\mathrm{specialized}}
  <R\,T_{\mathrm{base}}.
\]

When $T_{\mathrm{specialized}}<T_{\mathrm{base}}$, this gives

\[
  R>\frac{T_{\mathrm{setup}}}
  {T_{\mathrm{base}}-T_{\mathrm{specialized}}}.
\]

The denominator is the time saved on each run. The specialization becomes worthwhile once those repeated savings exceed its one-time setup cost.

Evaluation must therefore measure both execution performance and the one-time cost of preparing a specialized strategy.

\subsection{Sparse and Irregular Computation}
\label{sec:sparse-irregular-computation}

Sparsity and irregularity describe different properties of a graph workload. \emph{Sparsity} means that relatively few of the possible edges exist. \emph{Irregularity} means that the stored edges produce uneven work or nonuniform memory-access patterns. A sparse graph can have a regular structure, such as every node having the same number of neighbors, while another equally sparse graph can have highly variable degrees.

In GNN computation, the connectivity can be sparse while the node feature matrix remains dense. Each stored edge may require access to an entire feature vector. Consequently, a sparse adjacency matrix does not necessarily imply a small working set or low memory traffic.

\subsubsection{Uneven Work Distribution}

For incoming-neighbor aggregation, let $d_v$ denote the number of contributions to node $v$, which is its in-degree:

\[
  d_v=\deg^{-}(v)=|\mathcal{N}(v)|.
\]

If each contribution contains $F$ feature elements, straightforward aggregation performs work proportional to

\[
  d_vF
\]

for that node. Summed over the graph, the contribution-processing work is proportional to $|E|F$, but this total does not describe how evenly the work is distributed.

Since each directed edge contributes to one destination, the average in-degree is

\[
  \overline{d}=\frac{|E|}{|V|}.
\]

This average alone can conceal substantial skew. Degree percentiles and the maximum degree help distinguish graphs whose typical nodes require little work but whose largest neighborhoods require much more.

Very small neighborhoods can leave a large thread group underused. Very large neighborhoods can require long reductions or cooperation between multiple groups. Splitting a large neighborhood can improve work distribution, but introduces the need to combine partial results. A useful execution strategy must account for this tradeoff.

\subsubsection{Indirect Memory Access}

Sparse traversal uses edge indices to choose which feature rows to read. Nearby edges may reuse the same source data, while scattered source indices can lead to accesses far apart in memory. Thus, reading each feature vector efficiently does not guarantee efficient access across the graph.

Reordering edges can change traversal order without changing connectivity. Renumbering nodes can also change where their feature rows are stored, provided that connectivity and node-associated data are remapped consistently. These transformations can improve locality, but their preparation cost and any required output remapping must be included in evaluation.

\subsubsection{Metadata and Coordination Costs}

Sparse computation requires index processing in addition to numerical operations. Edge indices and row pointers must be read, and feature addresses must be calculated. These costs are especially relevant when each edge carries little arithmetic work.

For example, sum aggregation with a narrow feature vector performs relatively few additions per edge. Index traffic and address calculation can then form a substantial part of the operation. Wider feature vectors spread the index cost across more numerical work, although they also increase feature traffic.

Coordination costs depend on how the work is assigned. Edge-based accumulation may require atomic updates when several edges target the same destination. Destination-based reductions may require synchronization among cooperating threads. Neither cost is determined by sparsity alone.

Sparse representations therefore save work by omitting absent edges, but do not automatically make the remaining computation efficient. The useful performance characteristics include how degrees vary, how source features are reused, and how contributions are combined. Profiling these characteristics provides a basis for deciding whether a graph would benefit from a different layout or execution strategy.

\subsection{Static vs. Dynamic Graphs}
\label{sec:static-vs-dynamic-graphs}

A graph is \emph{static} for an execution workload when its topology remains unchanged across the runs being considered. The same nodes and edges are reused, although node features or edge-associated values may change. A graph is \emph{dynamic} when nodes or edges are added, removed, or replaced during that workload.

These definitions concern connectivity rather than whether every input value is constant. A fixed road network with changing measurements at its nodes can be a static graph workload. A graph whose edges are recomputed from the current measurements is dynamic, even if the number of nodes remains unchanged.

\subsubsection{Reusing Topology Analysis}

A static graph allows structural analysis to be performed before repeated inference. Its degree distribution, incoming neighborhoods, and connectivity-based ordering remain valid while the topology is unchanged.

This information can support preparation such as converting an edge list into a destination-grouped representation or partitioning nodes according to neighborhood size. It may also guide the selection of an aggregation strategy. Preparation need not depend on the current feature values when it uses only connectivity.

The resulting representation or execution plan can then be reused. As discussed in the preceding subsection on GPU computation, any execution savings must be large enough to recover the preparation cost over the expected number of runs. A strategy that benefits frequent inference may be unsuitable for a graph processed only once.

Static topology does not make every execution decision permanent. A change in feature width or data type can affect the appropriate kernel configuration even when connectivity is identical. Changes to the model or target hardware may likewise require a different plan.

\subsubsection{Changing Connectivity}

When topology changes, previously computed structural information may become invalid. Adding an edge changes the neighborhood of its destination and may alter degree-based work assignments. Removing or renumbering nodes can also invalidate indices and feature mappings.

If connectivity changes, any affected prepared representation or execution plan must be rebuilt or updated before it is reused.

Topology can also change because of the execution procedure. For example, selecting a different subset of neighbors for each run produces changing computation graphs even if the underlying dataset is fixed. Such a workload cannot necessarily reuse a plan specialized to one selected edge set.

A fixed underlying graph is therefore insufficient by itself. The relevant question is whether the connectivity actually consumed by the optimized operation remains unchanged.

\subsubsection{Validity of Specialized Execution}

A topology-dependent representation or plan must be associated with the graph for which it was prepared. Reusing it after connectivity changes can produce incorrect results, not merely lower performance.

The system must ensure that a prepared plan is used only with the graph it was built for, for example by requiring its connectivity to remain fixed while the plan is in use.

Changes to numerical values require separate consideration. A plan based only on connectivity may remain valid when node features change. If preprocessing incorporates edge weights or other values, changes to those values may also require rebuilding the prepared data.
